# Роли и права групп Sombra

## Статус

Включено в опубликованную **0.1.17** с согласованным обновлением backend и клиента; [запись выпуска](RELEASE-STATUS.md). Новый клиент на старом сервере показывает матрицу только для просмотра и не вызывает неподдерживаемые операции.

## Модель доступа

- **Владелец** определяется неизменённым `group.owner`, а не названием роли. Имеет все управленческие права. Только он создаёт, редактирует, удаляет роли и назначает их участникам.
- **Участник** — обязательная неизменяемая роль с `permissions: []`. Чтение, отправка сообщений, голос и собственные сообщения работают как раньше. Просмотр/копирование приглашения теперь требует эффективного `members.invite`: это намеренное изменение прежнего доступа обычных участников.
- Владелец включает «Разрешить обычным участникам приглашать людей» в разделе «Роли и разрешения» настроек группы. По умолчанию выключено, включая legacy-группы. Включение добавляет `members.invite` всем человеческим участникам поверх роли, не меняя определения ролей; боты не получают это право. Выключение не отменяет явный grant роли или все права владельца.
- **Администратор** — шаблон со всеми 12 управленческими разрешениями. Сам по себе шаблон никому не выдаётся.
- Владелец может создавать собственные роли и выбирать любой набор из 12 разрешений. У каждого человека одна назначенная роль, без наследования между ролями; глобальная политика приглашений добавляет только `members.invite` к эффективным правам человека. Всего до 32 ролей; имя 1–40 символов.
- Владелец не может быть назначен в другую роль; боты не получают человеческие роли. Администратор не может редактировать роли или повысить себя.

| Разрешение | Действие |
| --- | --- |
| `group.rename` | Изменить название группы |
| `group.avatar` | Изменить или удалить аватар группы |
| `channels.create_text` | Создать текстовый канал |
| `channels.create_voice` | Создать голосовой канал с чатом |
| `channels.rename` | Переименовать канал |
| `channels.delete` | Удалить канал и его содержимое |
| `members.invite` | Добавить человека по email, получить и скопировать код приглашения |
| `invite.rotate` | Заменить код приглашения, отключив прежний |
| `members.kick` | Исключить обычного участника |
| `messages.delete_any` | Удалить для всех чужое сообщение в группе |
| `stickers.manage` | Управлять групповыми стикерами/наборами |
| `bots.manage` | Управлять подключениями ботов в группе |

Редактировать чужие сообщения нельзя даже модератору. Право модерации не распространяется на личные диалоги и чужие группы. Удаление только для себя остаётся доступным как раньше. Исключение не является баном: действующее приглашение позволяет вернуться; при необходимости обновите код. Администратор не исключает владельца, других участников с управленческими правами, себя или ботов. Владелец может исключить администратора. Для выхода используется `leave_group`; владелец выйти не может. Смена владельца и канальные read-only/visibility ACL в эту модель не входят.

Права на подключения ботов не позволяют читать/менять ключи чужих ботов. Современный бот сохраняет отдельного владельца учётных данных. Удаление установки ограничено текущей группой; legacy-бот ограничен своим каналом. Действующая интеграция Hermes и её offline provisioning совместимы с моделью.

## API

Все операции требуют человеческую сессию; bot bearer не подходит. Проверки выполняются сервером заново, независимо от того, что показывает или присылает клиент.

`state.groups[]` и результаты групповых операций содержат:

```ts
roles: {id:string;name:string;permissions:GroupPermission[]}[];
memberRoles: Record<string,string>;
rolesRevision: number;
membersCanInvite: boolean; // private DB member_invites, default false
invite: string; // '' без эффективного members.invite
permissions: GroupPermission[]; // только эффективные права текущего запрашивающего
```

Новые операции:

- `save_group_role {group,role?,name,permissions,revision}` — без `role` создаёт UUID; только владелец.
- `delete_group_role {group,role,revision}` — только владелец; все назначенные участники явно возвращаются в «Участник».
- `set_group_member_role {group,user,role,revision}` — только владелец, человек уже должен быть в группе.
- `kick_group_member {group,user}`, `leave_group {group}`.
- `rotate_group_invite {group}`.
- `set_group_member_invites {group,enabled:boolean,revision:number}` → нормализованный Group DTO. Только владелец, даже администратор со всеми 12 правами не может менять политику. Строгие boolean и ожидаемая `rolesRevision`; успешная запись увеличивает эту версию. Сохранение атомарно под общим mutex, при ошибке откат. `update_group` не принимает изменения политики через посторонние поля.

Переход true → false заменяет общий код UUID: прежние ссылки **всех**, включая владельца/администратора, становятся недействительными; интерфейс должен предупреждать владельца. Повторная false-запись и первоначальная legacy false-миграция не вращают код. Уже известный старый код может работать до ротации: скрытие DTO не позволяет «забыть» ранее скопированную ссылку. `join_group` по действующему общему коду остаётся доступен вошедшему человеку и при false — владелец/администратор/роль с явным `members.invite` могут выдавать приглашения. Все Group DTO (создание, вход, state, изменения) скрывают код без эффективного права; сырой `member_invites` не публикуется.

На старом сервере/в старом native/local backend без новой возможности переключатель недоступен; матрица остаётся только для чтения. Новый grant не добавляется в массив прав роли «Участник».

Для изменений ролей `revision` обязателен и должен совпадать с текущим `rolesRevision`; конфликт возвращает `ROLES_REVISION_CONFLICT`. Интерфейс сохраняет несохранённую форму, обновляет данные и предлагает перепроверить изменения. Клиент не заменяет более новую матрицу медленным предыдущим ответом состояния.

Проверки существующих `update_group`, `create/update/delete_channel`, `invite_group_member`, `import/remove_sticker_pack`, модерации и управления ботами переведены на матрицу. Название и аватар проверяются независимо и до изменения данных: запрещённое поле в общей операции отклоняет всю запись. Тип нового канала строго `text` или `voice`.

## Совместимость и интерфейс

Группы без полей ролей получают нормализованные шаблоны, **пустые назначения** и прежний owner-only доступ. Автоматического повышения пользователей нет. При исключении/выходе очищаются назначение роли, голосовое присутствие и ожидающие сигналы группы; история сообщений сохраняется.

Единая модалка настроек группы оформлена как настройки пользователя: слева «Общее» (аватарка, название и переход к стикерам) и «Роли и разрешения» (матрица, назначения участников и общий переключатель приглашений). Общая область и тело прав прокручиваются внутри окна; подложки двух модалок не вкладываются. Кнопка «Роли и права» в шапке/контекстном меню сразу открывает второй раздел, обычная шестерёнка — первый. Участники видят матрицу только для чтения; владелец управляет ролями и назначениями. В списке участников показана роль. Создание голосовых и текстовых каналов разделено; настройка канала, удаление, стикеры, приглашения и поля имени/аватара отображаются/разрешаются по отдельным правам. При отзыве разрешения кнопки пересчитываются, но окончательный отказ всегда обеспечивает API.
