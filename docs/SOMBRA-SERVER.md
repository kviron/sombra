# Сервер Sombra

Развёрнут и проверен 15 ноября 2026 года.

- API: `POST https://sombra.mi-nerva.ru/api`. Принимает JSON с полем `op`. Вход устанавливает cookie `mines_session` с флагами `Secure`, `HttpOnly` и `SameSite=Strict`. Клиент должен сохранять и отправлять эту cookie в следующих запросах.
- Проверка: `curl -fsS https://sombra.mi-nerva.ru/health`. Текущий ответ — `Mines ready`. В исходниках ещё используются технические имена `mines-server` и `MINES_*`.
- systemd: `sombra.service`, включён в автозагрузку. Бинарник — `/usr/local/bin/sombra-server`, настройки — `/etc/sombra/sombra.env`. Статус: `systemctl status sombra`. Журнал: `journalctl -u sombra -n 100 --no-pager`.
- Nginx: `/etc/nginx/sites-available/sombra.mi-nerva.ru`. Проксирует `/api` и `/health` на `127.0.0.1:3847`. Корень `/` возвращает 404. Сертификат Let's Encrypt обслуживает существующий `acme.sh` с перезагрузкой Nginx при обновлении. Версия — NGINX Open Source 1.30.7 из репозитория nginx.org (обновление 19 ноября 2026, см. ниже).
- Данные: `/var/lib/sombra`. Начальные данные владельца хранятся на сервере в `/var/lib/sombra/FIRST-USER.txt`. После первого входа нужно сменить пароль. SSH-доступ хранится в корневом `.env`. Используй его локально для подключения и не копируй секреты в репозиторий или клиент.

При развёртывании проверены публичный HTTPS, ответ 401 для запроса без сессии, вход, авторизованный запрос `me` и выход.

## Файловая диагностика

Сервер сохраняет диагностику в `diagnostics.jsonl` и `diagnostics.previous.jsonl` в каталоге данных Sombra (`/var/lib/sombra` на рабочем сервере). Windows-клиент хранит файлы с теми же именами в `%APPDATA%\local.mines.chat`. Это технические события, не запись звонков: звук, текст сообщений, токены и параметры запросов не сохраняются.

Каждый файл ограничен 64 КиБ. Записи старше 48 часов очищаются при запуске и периодически во время работы; при большом потоке событий ротация по размеру может удалить записи раньше. Это не меняет сроки хранения системного журнала и уже записанных в него событий.

## Обновление

Из `` собери Linux-бинарник командой:

```sh
docker build --platform linux/amd64 --target server-export --output type=local,dest=server-release .
```

На сервере останови `sombra.service`, сделай приватную резервную копию всей `/var/lib/sombra`, установи собранный `server-release/mines-server` в `/usr/local/bin/sombra-server` с правами `755`, запусти сервис и проверь `/health`. Сохраняй действующие настройки в `/etc/sombra/`. С файловой базой одновременно должен работать только один процесс.

## NGINX 1.30.7 — 19 ноября 2026

18 ноября 2026 года F5/NGINX раскрыли уязвимости HTTP/2: **CVE-2026-123007** (целочисленное переполнение в управлении потоком HTTP/2 → переполнение кучи, CVSS 4.0 — 9.2 critical, CVSS 3.1 — 8.1; возможно выполнение кода при обходе ASLR) и **CVE-2026-123633** (use-after-free при проксировании HTTP/2, тот же CVSS 4.0 — 9.2). Исправления — 1.30.7 (stable) и 1.31.9 (mainline). В Ubuntu 24.04 на 19 ноября `nginx` 1.24.0-2ubuntu7.19 остаётся уязвимым и обновления ещё нет, а HTTP/2 был включён на всех трёх хостах при `worker_connections 768` (условие второй уязвимости). Поэтому установлена официальная сборка nginx.org.

- Репозиторий: `/etc/apt/sources.list.d/nginx.list`; ключ — `/usr/share/keyrings/nginx-archive-keyring.pgp`.
- Установлено `nginx 1.30.7-1~noble` вместо `1.24.0-2ubuntu7.19`. Пакеты `nginx-common` и `libnginx-mod-stream` удалены как конфликтующие; модуль stream встроен в сборку nginx.org и в конфигурации не использовался.
- `/etc/nginx/nginx.conf` восстановлен из резервной копии: пакет ставит свой файл без `sites-enabled` и с `user nginx`. Осталось `user www-data` и `include .../sites-enabled/*`; `include .../modules-enabled/*.conf` сохранён, каталог пуст.
- Удалён `/etc/nginx/conf.d/default.conf` из пакета (лишний сервер по умолчанию на порту 80). В `/etc/logrotate.d/nginx` пользователь `nginx` заменён на `www-data`, иначе после ротации логи стал бы писать несуществующий владелец. В `mime.types` возвращены `ogv` и `mkv`.
- HTTP/2 переведён на директиву `http2 on;` вместо `listen 443 ssl http2;` в конфигурациях `sombra`, `llm` и `vpn-panel`: параметр `http2` у `listen` устарел. gRPC для `vpn.mi-nerva.ru` по-прежнему работает по HTTP/2.
- Резервные копии: `/root/nginx-backups/nginx-etc-20261119T000034Z.tar.gz`, `/root/nginx-backups/preinstall-20261119T000211Z/`; журнал установки — `/root/nginx-backups/install-20261119T000211Z.log`.
- Проверено: `https://sombra.mi-nerva.ru/health` → 200 `Mines ready` по HTTP/2, `/api` без сессии → 401, `latest.json` → 200, `llm.mi-nerva.ru/v1/models` без токена → 401, 20 запросов по публичному адресу — 20 из 20. `nginx`, `sombra`, `coturn`, `roxy-hermes` активны, nginx включён в автозагрузку.
- Оговорка: при замене пакета nginx.org перезаписал `nginx.conf`, поэтому HTTPS был недоступен около минуты (01:02–01:03 CET). После восстановления конфигурации служба поднята; сейчас `nginx.conf` — локально изменённый conffile пакета `nginx`, и при обновлении nginx его нужно сохранять.
- `unattended-upgrades` обновляет только `noble-security` Ubuntu, поэтому nginx из nginx.org сам не обновится: нужен `apt-get update && apt-get install --only-upgrade nginx`. Если при обновлении спросят про `nginx.conf`, выбирать сохранение текущего файла.

## Хранение релизов — только последняя версия

На VPS остаётся один актуальный **опубликованный** выпуск. История установщиков хранится в
GitHub Releases; старые каталоги и staging-файлы на сервере не нужны. Политика изменилась
при выпуске 0.1.33: до него на сервере лежали пять последних версий.

Политика установлена как `/usr/local/lib/sombra-release-retention.py`; исходник —
`deploy/release-retention.py`. Без аргументов показывает план, с `--apply` выполняет очистку.
По умолчанию остаётся одна версия; `--keep N` позволяет временно сохранить больше.
`deploy/publish-*.sh` вызывает её **после успешной проверки HTTPS установщика и
stable-манифеста**. При создании следующих publisher-скриптов сохраняйте этот завершающий
вызов: `python3 /usr/local/lib/sombra-release-retention.py --apply`.

Обрабатываются только проверенные каталоги semver под `/var/www/sombra-updates` и старые
установщики/версионные манифесты в `/root/sombra-attachments-stage`. Непубликованные новые
версии не вытесняют стабильную. Симлинки, неожиданные файлы и удаление версии, на которую
ссылается stable-манифест, блокируют очистку. Используется flock и контроль неизменности
манифеста. Данные `/var/lib/sombra`, приватные резервные копии `/root/sombra-backups`,
локальные сборки и GitHub-релизы не удаляются. Старые прямые ссылки на VPS больше не
доступны; обновление старого клиента через актуальный `latest.json` остаётся возможным.

Текущий `latest.json`, его установщик и подпись проверяются после очистки; сервис при этом
не перезапускается.

При выпуске 0.1.33 очистка оставила только `0.1.33`: удалены каталоги 0.1.24–0.1.32 и
связанные staging-файлы, 99 671 800 байт. Предыдущий stable-манифест сохранён в
`/root/sombra-backups/release-manifest-20261123T115329Z/`. Новый установщик, подпись и
`latest.json` проверены по HTTPS после очистки; на VPS осталось 12 МБ каталога обновлений
(включая тестовый WAV).

### Мониторинг голосового тракта

Обновлённый клиент отправляет в существующий `diagnostics_report` только фиксированные события `voice_transport` и `voice_output`: смену состояния ICE, прямой маршрут или TURN, подозрение на остановку/восстановление передачи аудиопакетов и переключения микрофона/звука. Это не проверка слышимости: растущие счётчики не подтверждают, что микрофон захватил речь или динамики её воспроизвели. Адреса, идентификаторы собеседников, содержимое пакетов и звук не отправляются.

Искать эти события следует в обоих серверных JSONL-файлах. Сопоставляйте их по времени с `voice_join`, `voice_poll`, `voice_signal` и журналом coturn (время на сервере может отличаться от МСК). Прокси/ICE может не выбрать ни одного маршрута; ошибки coturn о закрытых приватных адресах сами по себе не считаются отказом TURN. Сначала обновляется сервер с новой схемой, затем клиенты; старый сервер отклоняет незнакомые события.

## Диагностика тестирования

Владелец сервера может отправить `POST /api` с телом `{"op":"diagnostics_recent"}` и своей действующей cookie `mines_session`. Доступ привязан к первой, созданной при инициализации учётной записи и сохраняется после смены её email. Ответ `data.events` содержит до 200 записей с временем в Unix-секундах, источником (`server` или `desktop`), операцией, категорией и HTTP-статусом. Порядок от старых записей к новым. При перезапуске сервиса история API сбрасывается.

На сервере `journalctl -u sombra -g sombra_diagnostic -n 100 --no-pager` показывает ошибки API с кодом 5xx и принятые отчёты клиента. В Windows локальный журнал клиента находится в `%APPDATA%\local.mines.chat\diagnostics.jsonl`. При заполнении файл до 64 КиБ сменяется новым, а предыдущий сохраняется как `diagnostics.previous.jsonl`.

Клиент записывает ошибки сети и HTTP, тайм-ауты, сбои хранения сессии, неожиданные ответы, необработанные ошибки WebView и ошибки доступа к устройствам голосовой связи. С действующей сессией клиент отправляет накопленные сбои партиями до восьми записей через `diagnostics_report`. Отправка доступна всем вошедшим пользователям, а сервер ограничивает приём 60 записями в минуту и проставляет время получения. Буфер отправки хранится в памяти процесса, а локальные файлы доступны после закрытия клиента. В записях есть только заранее определённые имена операций и категорий, код статуса и время.

## Сервер и клиент 0.1.25: аватары вне снапшота (21 ноября 2026)

Причина правки — измеренная нагрузка. За 21 ноября `POST /api` дал 387 752 запроса и 64,9 ГБ; в активные часы 4,6–4,9 ГБ/час, в 17:00 — 11,4 ГБ. Основной вклад — снапшот `state` весом 1 230 005–1 230 247 байт, который клиент запрашивает каждые две секунды. В базе хранились data-URL аватары 180/200/92/216 КБ у четырёх пользователей и 175 КБ у группы: около 860 КБ из 1,23 МБ были одними и теми же картинками. Предыдущий процесс сервиса израсходовал 9 ч 41 мин CPU за 2 суток 22 часа.

Что изменено:
- `state {avatar_assets:true}` отдаёт `avatar:""` и `avatarHash` (base64url SHA-256 без паддинга) вместо картинки. Без флага ответ прежний, поэтому установленный клиент 0.1.24 ничего не теряет.
- Новая операция `avatar_file {kind,id,sha}` проверяет сессию, членство в группе и совпадение текущего хеша. Хеш — ключ кэша, а не полномочие. Проверено на локальной сборке: состояние с аватаром 60 КБ — 121 283 байта против 1 357 байт в компактном режиме, `avatar_file` вернул сохранённые байты, чужой хеш — `AVATAR_NOT_FOUND` (404), без сессии — 401.
- Клиент 0.1.25 кэширует картинки по хешу, не повторяет неудачную загрузку на каждом опросе и получает отдельный тайм-аут `state` — 30 с.
- Транспорт клиента сжимает ответ (reqwest, gzip), nginx сжимает JSON и проксированные ответы: `latest.json` 1030 → 703 байта. Ответы 401 не сжимаются по правилу nginx (gzip только для 200/403/404), успешный `state` — сжимается.
- Хелпер Яндекса пишет причину отказа одной обезличенной строкой (URL вырезаются). Раньше все 502 были недиагностируемыми.
- Проверка после выкладки: `health` 200, `state` и `avatar_file` без сессии — 401, `nginx -t` успешен, `sombra`, `sombra-yandex-stream` и `nginx` активны. Бэкап бинарника, базы, журнала и unit-файла — `/root/sombra-backups/release-0.1.25-20261121T190018Z/`, копии nginx.conf и хелпера — в `/root/sombra-backups/` с меткой `20261121T190*Z`.
