# Локальный кэш вложений Sombra

## Статус и назначение

Включено в опубликованную 0.1.17. Кэш использует авторизованную историю и существующий `attachment_file`; отдельное серверное хранилище кэша не добавляется. Актуальная запись публикации — [RELEASE-STATUS.md](RELEASE-STATUS.md).

Кэш хранит **только уже загруженные** вложения: просмотренные изображения и скачанные файлы. Массовой фоновой загрузки всей истории нет. Если серверная очистка удалила тело файла, но сообщение и доступ к нему сохранились, локальная копия остаётся доступной с отметкой «Локальная копия · файл очищен на сервере».

Это не резервная копия и не восстановление серверной истории: незагруженный, повреждённый или вытесненный файл восстановить нельзя. Очистка кэша необратима для файлов, уже отсутствующих на сервере. Данные не отправляются обратно на сервер и не передаются другим участникам автоматически.

## Отображение изображений

Картинки в переписке показаны без имени файла, файловой строки и подложки сообщения, как стикеры. У сообщения с картинкой и текстом подложка остаётся только у подписи. Нажатие открывает единый увеличенный просмотр с сохранением пропорций; в чате и просмотре скачивание появляется поверх картинки при наведении или фокусе (на сенсорном устройстве доступно постоянно). Обычные файлы сохраняют имя, размер и свою кнопку. Просмотр закрывается Escape, крестиком или нажатием снаружи, фокус возвращается к картинке. Скрытие/удаление доступного сообщения убирает и его просмотр; объектные URL освобождаются.

Отменённый ответ предыдущей нативной сессии отличается от настоящего `AUTH_REQUIRED`: поздняя загрузка аккаунта A не разлогинивает уже открытый аккаунт B.

## Настройки → Данные и память

- Объём и количество файлов текущего аккаунта.
- Лимит на этом устройстве: выключено / 256 / 512 / 1024 / 2048 / 4096 МиБ. По умолчанию 1024 МиБ.
- LRU: при заполнении вытесняются ранее использованные локальные копии, а не сообщения.
- Выключение очищает кэш аккаунта; отдельная очистка требует подтверждения.
- Аккаунты и их лимиты разделены. Очистка не затрагивает копии другого аккаунта и экспортированные вручную файлы в «Загрузках».
- Открытый предпросмотр может оставаться в памяти; повторно открытый доступный файл может снова попасть в кэш.

## Доступ и конфиденциальность

Серверный TTL и удаление сообщения — разные операции. Кэш разрешён только для вложения из последнего принятого полного снимка истории текущего аутентифицированного аккаунта, с совпадающими message ID и attachment ID/метаданными. В сообщении с несколькими файлами каждый файл имеет собственный ключ кэша и отметку доступности. Перед новым чтением снимок старше пяти секунд перепроверяется. Если перепроверка недоступна, содержимое не возвращается: это **не автономный офлайн-архив**.

Удаление/скрытие сообщения, выход или исключение из группы убирает его из разрешённого снимка и очищает соответствующие копии. Уже обнаруженный отказ доступа (401/403 и ошибка видимости сообщения, которую текущий сервер может вернуть с HTTP400) аннулирует разрешение немедленно. Ошибка только истёкшего срока хранения не аннулирует права на локальную копию.

Выход/смена аккаунта и поздние ответы не смешивают пространства аккаунтов. Очистка/смена лимита имеют отдельную эпоху записи: уже начатый сетевой запрос не наполняет очищенный кэш заново и не должен отменять обычную действующую сессию. Удаление сообщения в приложении не может отозвать файлы, ранее самостоятельно экспортированные человеком: это не DRM.

## Настольный Windows-клиент

Нативный `remote_api` обрабатывает снимки состояния и `attachment_file`. Авторизация и область аккаунта выводятся из нативной сессии, не из пользовательского параметра JS. `save_message_attachment` использует тот же путь чтения, поэтому повторное сохранение и восстановление после TTL работают через общий кэш.

Данные находятся в приватном каталоге `attachment-cache` рядом с нативной сессией приложения; каталоги/ключи хешированы по аккаунту, сообщению и вложению. Содержимое защищено Windows DPAPI, проверяются целостность, метаданные и лимит 10 МиБ. Атомарная запись, квота/LRU, обработка повреждений и отказ следовать симлинкам/reparse points ограничивают операции каталогом кэша. Сбой кэширования не должен ломать обычную сетевую загрузку.

Сообщения старше окна снапшота доступны через страницы истории. При поддержке сервером `features.attachmentMetadata` нативный клиент читает такое вложение по сети и после передачи подтверждает видимость сообщения и идентичность файла запросом `attachment_file` с `metadata_only`. Дисковый кэш продолжает использовать файлы из актуального снапшота.

Нативные команды:

- `attachment_cache_info` → `{enabled,limitMiB,bytes,files}`;
- `set_attachment_cache_limit {limitMiB}` → такой же результат;
- `clear_attachment_cache` → такой же результат.

Сведения/очистка/лимит могут работать без сети для уже установленного нативного аккаунта, пока его сессия не сброшена. Чтение тела файла по-прежнему требует актуального подтверждения видимости. Длительная передача файла не блокирует получение истории и выход из аккаунта; перед возвратом тела файла права перепроверяются.

## Браузер

IndexedDB хранит метаданные и тела в отдельных object stores. Снимки истории, статистика, очистка и LRU не читают все тела файлов. Контекст доступа привязан к принятому аккаунту; настройка и очистка ограничены им. Неподдерживаемая/переполненная IndexedDB не мешает обычным сетевым загрузкам, но кэш при этом недоступен. Браузерное хранилище защищается политикой origin и профилем браузера, не Windows DPAPI.

- `check-attachment-cache.mjs`: изолированные IDB-тесты областей аккаунтов, сохранения/повреждения/видимости, очистки/лимитов, эпох и held-HTTP гонок.
- `check-attachment-cache-browser.mjs`: **16 проверок пройдено** на финальном `index-jtQZvOq6.js`, без ошибок страницы. Реальная IndexedDB и собранный UI (фото, повторный запуск, ZIP, TTL и просмотр, настройки и недоступное хранилище); дополнительные API-пробы используют отдельный singleton исходного TS-модуля. Три размера окна без горизонтального переполнения. Стенд изолирован от production.
- Нативные cache/HTTP-тесты проверяют DPAPI, пути/квоты/LRU, отзыв доступа, свежесть, смену сессии и поздние ответы. Финальный полный `cargo test --bin mines-chat`: **56 пройдено**, включая 10 cache/HTTP-проверок.
- Финальные JS-регрессии: **33 теста пройдено**, дополнительно 80 проверок helper ролей. `tsc --noEmit`, Vite и локальный Windows release build завершены успешно. Это не ручная проверка на пользовательской периферии; production не менялся.
