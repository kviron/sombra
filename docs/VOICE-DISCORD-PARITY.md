# Голос в Discord и в Sombra: сверка

Источники: официальная спецификация **Discord Voice Connections** (`docs.discord.com`, раздел
Voice Connections) и открытая реализация [discordjs/voice](https://github.com/discordjs/voice)
(`src/networking/VoiceWebSocket.ts`, `VoiceUDPSocket.ts`, `Networking.ts`, `VoiceConnection.ts`).
Репозиторий `morluto/rea` — инструмент для реверса, своей реализации голоса не содержит; он
полезен, чтобы разбирать клиент, но протокол документирован открыто.

## Как устроен звонок в Discord

1. **Основной gateway.** Клиент отправляет `Voice State Update` с `channel_id`. В ответ приходят
   два события: `VOICE_STATE_UPDATE` (`session_id`) и `VOICE_SERVER_UPDATE` (`token`, `endpoint`)
   — адрес выделенного голосового сервера для этого звонка.
2. **Голосовой WebSocket.** Подключение к `wss://<endpoint>?v=4`.
   - `op 8 Hello` — интервал heartbeat; клиент шлёт `op 1 Heartbeat` с nonce, ждёт `op 6
     Heartbeat ACK`. Три пропущенных ответа — разрыв соединения (`VoiceWebSocket.ts`, 170–176).
   - `op 0 Identify` — `{server_id, user_id, session_id, token}` (токен одноразовый, на этот звонок).
   - `op 2 Ready` — `{ssrc, ip, port, modes}`: SSRС, адрес голосового UDP и поддерживаемые
     шифры.
3. **UDP и проверка адреса.** Клиент открывает UDP-сокет и делает IP discovery: пакет
   `type=1, length=70, ssrc`, сервер отвечает `type=2` со внешним IP и портом
   (`VoiceUDPSocket.performIPDiscovery`). Найденный адрес сообщается обратно.
4. **Выбор протокола.** `op 1 Select Protocol` → `{protocol:"udp", data:{address, port,
   mode}}`, где `mode` — первый поддерживаемый из списка, обычно
   `xsalsa20_poly1305_lite`.
5. **Ключ шифрования.** `op 4 Session Description` → `{mode, secret_key}`. Кадры шифруются
   AEAD: nonce дописывается в конец пакета (`lite` — 4 байта, счётчик), `suffix` — 24 байта,
   базовый режим — nonce из RTP-заголовка (`Networking.ts`, 543–558).
6. **Медиа.** RTP: 12-байтовый заголовок (версия, payload type 120, `sequence`, `timestamp`
   48 кГц, `ssrc`) и зашифрованный Opus-кадр, обычно 20 мс.
7. **Речь.** `op 5 Speaking` сообщает флаг речи и SSRC — по нему у остальных загорается
   индикатор.
8. **Живучесть UDP.** Keepalive каждые 5 с с 32-битным счётчиком; 12 неподтверждённых
   подряд — сокет закрывается (`VoiceUDPSocket.ts`, 30–35).
9. **Переподключение.** Состояния `Signalling → Connecting → Ready → Disconnected /
   Reconnecting / Resuming`; коды закрытия 4014 (не переподключаться), 4015 (resume),
   4016 (новый Identify) (`VoiceConnection.ts`).
10. **Ключевое свойство:** медиа **никогда не идёт напрямую между клиентами**. Голосовой сервер
    Discord ретранслирует звук всем участникам. Поэтому «слышу его, а он меня нет» из-за NAT
    там невозможно в принципе.

## Как устроено у нас

WebRTC: Opus и AEAD уже внутри (DTLS-SRTP), ICE со STUN и TURN, сигнализация — HTTP-опрос
`voice_poll` каждые 700 мс, медиа по умолчанию идёт **напрямую** между участниками.

| Discord | Sombra | Состояние |
|---|---|---|
| Выделенный голосовой сервер, медиа всегда через него | TURN-релей есть (coturn, одноразовые ключи), но ICE предпочитает прямое соединение | **выровнено** с 0.1.28: режим «Всегда через сервер» |
| `op 8/1/6` heartbeat, 3 пропуска → разрыв | ICE-состояния + `ice_disconnected` в журнал | частично |
| `op 0 Identify` с одноразовым токеном | `voice_join` с сессией; TURN-креды на 12 часов | выровнено |
| UDP keepalive 5 с, 12 пропусков | WebRTC ICE keepalive | внутри библиотеки |
| Переподключение по кодам, resume | повторное подключение вручную (кнопка), авто-reconnect нет | **не выровнено** |
| `op 5 Speaking` → индикатор речи | локальный уровень микрофона; удалённая речь — по `peer.muted` | **не выровнено** |
| Громкость каждого участника отдельно | одна громкость комнаты | **не выровнено** |
| E2EE (DAVE/MLS) в новых версиях | DTLS-SRTP шифрование транспорта, без E2EE поверх | осознанно не делаем |

## Что изменено этим выпуском

В P2P-комнатах `src/features/voice-room/model/peer-signaling.ts` применяет настройку
«Соединение → Всегда через сервер» при создании каждого соединения. Если настройка включена
и `voice_join` вернул TURN, клиент задаёт `iceTransportPolicy: "relay"`. По умолчанию
разрешены все доступные маршруты. В пилотной комнате LiveKit звук всегда проходит через SFU.

Почему это важно: прямой путь может «сойтись» по ICE и при этом не пропускать звук в одну
сторону (асимметричный NAT, фильтрация UDP). Пакеты при этом считаются отправленными, журнал
чист, а собеседник молчит. Релей убирает этот класс отказов целиком.

## Что осталось для полного паритета

1. **Автоматическое переподключение** при `ice_failed` / `disconnected` с экспоненциальной
   паузой — сейчас нужен повторный вход в канал.
2. **Индикатор речи удалённых участников** по `audioLevel` из `inbound-rtp` (аналог `op 5`).
3. **Громкость отдельного участника** (0–200%) поверх общей громкости комнаты.
4. **Проверка приёма** в журнале: пакеты приходят, но энергии нет → `audio_receive_silent`.

Первые три — независимые задачи, каждая не требует менять транспорт. Четвёртая дополняет
существующую проверку отправки.
