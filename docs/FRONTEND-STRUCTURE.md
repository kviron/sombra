# Структура фронтенда (Feature-Sliced Design)

Фронтенд разложен по [Feature-Sliced Design](https://fsd.how) v2.1. Документ отвечает на два вопроса: куда положить новый код и почему текущие файлы лежат именно так. Правила проверяются автоматически: `npm run check:fsd`.

## Слои

Слои идут сверху вниз; модуль может импортировать только то, что ниже него.

| Слой | Что содержит | Пример |
| --- | --- | --- |
| `app/` | Инициализация, провайдеры, глобальные стили, оконная оболочка Tauri, dev-стенды | `App.tsx`, `layout/title-bar.tsx`, `styles/glass.css` |
| `pages/` | Композиция экрана/маршрута: страница собирает срезы нижних слоёв | `pages/chat` |
| `features/` | Действие пользователя с собственной ответственностью и UI | `features/voice-room`, `features/message-composer` |
| `entities/` | Бизнес-модель предметной области и её канонический UI | `entities/message`, `entities/conversation` |
| `shared/` | Инфраструктура без бизнес-правил: UI-кит, утилиты, транспортные типы | `shared/ui`, `shared/api`, `shared/lib` |

`widgets/` не используется: официальный справочник слоёв его не рекомендует, а ответственность пересекается с `features` и `pages`. Блоки, которые нужны только одной странице, остаются в её срезе.

## Срезы

```
src/
  app/
    App.tsx  entrypoint.tsx  direct-message-popup.tsx
    layout/              заголовок окна, кнопки окна, ручки ресайза, переключатель темы
    lib/                 window-actions (обёртки над Tauri)
    model/               use-window-maximized
    styles/              index.css, glass.css, settings.css, chat-extras.css, hologram.css
    theme/               ThemeProvider, useTheme
    dev/avatar-fx-preview/  стенд предпросмотра эффектов аватара (вне сборки приложения)
```

`app/entrypoint.tsx` и `app/direct-message-popup.tsx` — две точки входа приложения: главное окно и окно-попап уведомлений (`direct-message-popup.html`). Обе создают свой React-корень, поэтому ни одна из них не входит в публичный API среза и не импортируется ниоткуда.

`app/providers/errorBaundari/` — граница ошибок (`ErrorBoundary` по документации React: `getDerivedStateFromError` + `componentDidCatch`) и провайдер `ErrorBoundaryProvider`, который оборачивает всё дерево в `entrypoint.tsx`: пишет сбой в журнал диагностики категорией `webview: render_error`, показывает экран восстановления и пересобирает поддерево по кнопке. В окне уведомлений та же граница оборачивает каждое уведомление отдельно, чтобы одно битое не гасило остальные. Ошибки обработчиков событий и промисов граница не ловит — их фиксирует `window.onerror` в `shared/api/diagnostics.ts`.

```
  pages/
    chat/                рабочее пространство: LiveChat, транскрипт, друзья, боты, участники, профиль, юзерлент
    login/  register/    формы входа и регистрации
    start/               прежний лендинг; маршрута нет (см. «Известные остатки»)
  features/
    account-settings/    настройки аккаунта: профиль, безопасность, медиа, украшения, кэш вложений, журнал, уведомления
    bots/                боты: настройки, доступ к инструментам, индикатор активности, подсказки команд
    conversation-list/   список переписок и создание диалога
    conversation-details/ сведения о переписке и её материалы
    group-management/    настройки группы и роли
    message-actions/     ответ, пересылка, правка, удаление, читатели
    message-composer/    поле ввода: вложения, стикеры, упоминания, ссылки, черновики
    notifications/       уведомления о личных сообщениях, всплывающее окно-попап
    updates/             проверка и установка обновлений
    voice-room/          голосовая комната: звонок, устройства, участники, музыка, звонки в диалогах
  entities/
    conversation/        присутствие собеседника, непрочитанные упоминания, правила уведомлений
    group/               каталог прав группы
    message/             текст, вложения, упоминания, ссылки, прочитанность, черновики упоминаний, материалы
    sticker/             библиотека стикеров и подсказки
    user/                строка пользователя, контекстное меню
  shared/
    api/                 backend.ts (транспортные типы и вызовы), tauri, диагностика, кэш вложений
    config/              ссылки
    lib/                 утилиты: ссылки в сообщениях, права, кроп изображений, музыкальные команды, user-actions
    ui/                  UI-кит: button, input, select, message, avatar-fx, elements-*
```

У каждого среза слоёв `pages`, `features`, `entities` есть `index.ts` — его публичный API. Если срезу нужна вторая точка входа (например, окно-попап не должно тянуть весь срез и его стили), рядом кладут `index.<окружение>.ts`: `features/notifications/index.popup.ts` отдаёт только тост и разбор адресата уведомления.

## Правила

1. **Импорт только вниз.** `app → pages → features → entities → shared`. Обратный импорт — ошибка.
2. **Публичный API среза.** Снаружи среза импортируют только из его `index.ts`: `@/entities/message`, а не `@/entities/message/ui/message-text`. Внутри среза — относительные пути.
3. **Между срезами одного слоя импортов нет.** Если двум срезам нужен общий код, он опускается ниже (в `entities`/`shared`), либо срезы объединяются, либо связывает их страница.
4. **Стили и вложения исключены из правила 1–3.** `.css`, `.wav`, `.png` подключаются там, где используются: это глобальные ресурсы, а не модульный API. Глобальные таблицы стилей лежат в `app/styles/`.
5. **`shared` не содержит бизнес-правил.** Права группы, категории материалов переписки и прочие правила продукта живут в `entities`. Транспортные типы (`ChatState`, `Dialog`, `User`) — можно: это контракт, а не правило.

## Куда класть новый код

| Что это | Куда |
| --- | --- |
| Компонент, нужный одной странице | в срез этой страницы: `pages/chat/ui/…` |
| Действие пользователя с собственным UI, нужное нескольким местам | `features/<действие>/` |
| Правило продукта над данными предметной области | `entities/<сущность>/model/` |
| Канонический вид сущности (строка сообщения, аватар, карточка) | `entities/<сущность>/ui/` |
| Кнопка, поле, диалог без бизнес-смысла | `shared/ui/` |
| Разбор текста, форматирование, работа с файлами | `shared/lib/` |
| Запрос к API, тип ответа | `shared/api/` |
| Провайдер, роутинг, глобальный стиль | `app/` |

Правило «сначала в страницу»: не выделяйте срез, пока код не понадобился в двух местах или пока у него нет собственной причины меняться.

## Осознанные решения

- **Срезы с одним потребителем.** Приложение — одно рабочее пространство, поэтому почти всё используется страницей `chat`. Срезы `features/*` и `entities/*` всё равно выделены: иначе страница превращается в 60+ файлов без границ, а каждый срез отвечает за свою причину изменений. Это отступление от строгого правила «одного потребителя» и оно сознательное.
- **`shared/lib/user-actions.tsx`.** Это контекст внедрения зависимостей (страница передаёт колбэки открытия профиля, дружбы, личных сообщений), а не правило пользователя. Поэтому он в `shared`, а не в `entities/user`: так `entities/message` и `features/voice-room` используют его без импорта между срезами.
- **`app/dev/avatar-fx-preview/`.** Стенд предпросмотра эффектов аватара. Раньше он лежал в `shared/ui/avatar-fx/preview` и импортировал код из `app` (импорт вверх). Теперь он в `app` и может импортировать что угодно; в сборку приложения не входит.
- **`shared/api/backend.ts`.** Содержит и вызовы, и все транспортные типы; его импортируют ~60 модулей. Разделение на `dto` и `requests` — следующий шаг, в перенос файлов он не входил.
- **Глобальные стили.** `glass.css`, `settings.css`, `chat-extras.css`, `hologram.css` подключаются один раз в `App.tsx`, чтобы порядок каскада остался прежним. Поэтому они лежат в `app/styles/`, а не рядом со срезами, которые их используют.

## Известные остатки

Не используются ни одним импортом и не подключены к маршрутам — кандидаты на удаление:

- `pages/start/` (`StartPage`, `MineField`) — прежний лендинг;
- `features/bots/ui/bot-command-suggestions.tsx`;
- `entities/conversation/model/new-direct-messages.ts`;
- `shared/lib/prepare-avatar.ts`;
- `shared/ui/elements-progress/range.ts`.

Удалены при рефакторинге: `src/app/chat-page.tsx` (демо-страница с битой кодировкой, дублировала `LiveChat`) и `src/components/button.tsx` (дубль `shared/ui/button`). История сохранена в git.

## Порядок стилей

Стили подключаются из компонентов, поэтому порядок правил в каскаде равен порядку вычисления модулей. Публичный API среза (`index.ts`) этот порядок задаёт, и перенос файлов может его изменить: после рефакторинга `account-approved.css` стал грузиться после нового дизайна карточки профиля и перебил его — окно настроек развалилось.

Правило: если компонент **переопределяет** стили соседнего компонента, его собственный `*.css` импортируют раньше импорта соседнего компонента, чтобы переопределение осталось последним в каскаде. Так сделано в `features/account-settings/ui/account-security.tsx`: там `account-approved.css` стоит первой строкой, а `profile-media-dialogs.css` подключается ниже и выигрывает.

Проверять это стоит глазами в браузере: статический анализ порядок каскада не отслеживает. Быстрый способ — сравнить вычисленные стили ключевого элемента до и после переноса.

## Связи с Rust-оболочкой

Перенос файлов во фронтенде затрагивает ещё два места, которые не проверяются `tsc`:

- **`include_bytes!` в Rust.** `src-tauri/src/notifications.rs` встраивает `src/features/notifications/assets/message-tone.wav` — путь жёстко прописан в коде. После переноса ассета его правят там же и проверяют `cargo check -p sombra --no-default-features`.
- **Ассеты через `new URL('./x.wav', import.meta.url)`.** Vite разрешает такой путь относительно файла-модуля, а не `import`. Поэтому при переносе модуля в подпапку путь правят на `../assets/x.wav`; искать такие места — `grep "new URL(" src`.

После переноса стоит убедиться, что `npm run build` кладёт `dist/assets/*.wav` — иначе звук молча не загрузится.

## Проверка

```bash
npm run check:fsd                 # границы слоёв и срезов
npx tsc --noEmit                  # типы
npm run test:src                  # модульные тесты (node --experimental-strip-types)
npm run build                     # prebuild + tsc + vite build
```

`check:fsd` стоит запускать в CI рядом с `tsc`, чтобы правило 1–3 не разрушалось со временем.
