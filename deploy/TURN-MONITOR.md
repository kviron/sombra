# Внешний мониторинг TURN

`turn-monitor.py` — одноразовая проверка с **внешнего** Linux-хоста (Python ≥ 3.9). Не устанавливайте на TURN-сервер: это не будет проверкой клиентского маршрута. Скрипт не запускает HTTP, не открывает входящих портов, не входит в Sombra и не меняет coturn, Nginx, firewall или API. Для рабочего Sombra в серверной документации указан `sombra.mi-nerva.ru:3478` (UDP/TCP), диапазон ретрансляции UDP `49160–49279`.

Для каждого клиентского транспорта (UDP и TCP) проба создаёт две аутентифицированные TURN Allocate с UDP-relay, ставит CreatePermission для обоих направлений и проверяет доставку двух отдельных случайных 32-байтных payload через TURN Send/Data Indication, включая адрес отправившего relay. Затем пытается закрыть обе аллокации (Refresh с Lifetime=0); при обрыве действует TTL сервера. TCP здесь означает **клиент → TURN по TCP**, а не RFC 6062 TCP-relay и не TLS. Проверка не заменяет тест WebRTC-звонка: ICE, DTLS/SRTP, TLS TURN, голос и весь диапазон relay-портов она не проверяет.

## Выбор внешней проверки

- **Предпочтительно:** настройте `peer` как второй, контролируемый вами TURN с отдельными учётными данными и независимым публичным маршрутом. Так обе стороны проверяют UDP relay через сеть между серверами без новых публичных endpoint'ов. Оба TURN должны разрешать relay-пакеты друг друга и уметь общаться по одному семейству IP. Отказ второго TURN может выглядеть как отказ проверки цели; следите за ним отдельно. Не подставляйте сторонние общедоступные TURN или сайты для тестирования ICE с рабочими учётными данными.
- **Без второго TURN:** опустите `peer`; проверятся внешний клиентский маршрут на `3478` и обмен двумя relay на одном сервере. Hairpin может не пересечь внешний firewall/NAT диапазона relay или не поддерживаться конфигурацией. Успех не подтверждает доступность диапазона из интернета, а отказ не обязательно означает сбой обычных звонков.
- **Проверка клиентского опыта:** отдельный звонок между двумя устройствами в независимых сетях с контролем фактически выбранной relay-пары. Используйте только доверенные клиенты и тестовых пользователей. Открытый порт, STUN Binding или HTTPS `/health` сами по себе не проверяют ретрансляцию.

## Секреты

Подготовьте JSON вне репозитория, например `/etc/sombra-turn-monitor/turn.json` (`root:root`, файл `0600`, каталог `0700`). Значения ниже — только шаблон, не рабочие секреты. `peer` имеет те же обязательные поля, что и `target`.

```json
{
  "target": {"host": "turn.example.com", "port": 3478, "username": "issued-username", "password": "issued-password"},
  "peer": {"host": "turn-peer.example.net", "port": 3478, "username": "peer-issued-username", "password": "peer-issued-password"}
}
```

Передавайте короткоживущую пару username/password из доверенного приватного процесса выдачи, с запасом TTL на запуск проверки, либо отдельные отозваемые данные мониторинга, если такой способ уже поддерживается TURN. Переиздавайте данные до истечения TTL: готовые systemd-юниты **не выдают и не обновляют** credentials. В действующей схеме Sombra временные пары 12 часов выдаются авторизованным пользователям при входе в голосовую комнату. Выдача новых мониторинговых данных — отдельное согласованное действие оператора; монитор не хранит пароль/сессию Sombra, не автоматизирует вход в комнаты и не получает `static-auth-secret` TURN. Не переносите мастер-секрет или SSH-доступ на внешний монитор. При ротации атомарно заменяйте файл с теми же правами. Не передавайте значения в аргументах, переменных окружения, URL, истории команд, логах или тикетах. Не пускайте probe через недоверенный TLS-терминатор или публичный сервис. Обычный TURN UDP/TCP передаёт username в сетевом пакете в открытом виде, но не пароль; используйте стойкие выданные пароли и минимальный TTL. Ограничьте доступ к журналам и сетевым дампам.

## Установка на внешний хост (systemd ≥ 247)

Из каталога `app/deploy` в уже согласованном окружении мониторинга:

```sh
sudo install -d -m 755 /usr/local/lib/sombra-turn-monitor
sudo install -d -m 700 /etc/sombra-turn-monitor
sudo install -m 644 turn-monitor.py /usr/local/lib/sombra-turn-monitor/turn-monitor.py
sudo install -m 644 turn-monitor.service turn-monitor.timer /etc/systemd/system/
# Provision /etc/sombra-turn-monitor/turn.json through your private secret store first.
sudo systemctl daemon-reload
sudo systemctl start turn-monitor.service
sudo journalctl -u turn-monitor.service -n 20 --no-pager
sudo systemctl enable --now turn-monitor.timer
```

Для ручного запуска с закрытым файлом текущего пользователя: `python3 -I -B turn-monitor.py --config /private/turn.json --transport both`. Монитор печатает JSON по строке на транспорт (`status`, `transport`, `stage`, `detail`, `elapsed_ms`), без имён, адресов, credential и сырых ответов. Код 0 — все выбранные транспорты работают, 1 — сбой хотя бы одного, 2 — ошибка конфигурации/аргументов. Срок по умолчанию — 3 с на отдельную операцию (не на весь тест); systemd ограничивает весь запуск 75 с. Настройте оповещения в существующем приватном сборщике по нескольким последовательным ошибкам, также отслеживая отсутствие свежих запусков. Для отмены: `sudo systemctl disable --now turn-monitor.timer`; секреты монитора нужно удалить или отозвать по процедуре оператора.

## Тесты

`python3 -B app/deploy/turn-monitor-test.py -v` из корня. Локальная loopback fixture проверяет UDP/TCP, аутентификацию, двустороннюю доставку, очистку, stale nonce, отказ при неверных credentials/целостности, блокировку reverse и несовпадение payload; есть независимый RFC 5769 вектор HMAC. Это не заменяет интеграционный тест с реальным coturn. Для него предварительно запустите отдельный coturn с тестовыми credentials в контролируемой среде; для проверки внешнего маршрута запустите монитор с другого хоста и используйте второй контролируемый TURN. Производственный запуск и изменения конфигурации в этот набор не входят.
